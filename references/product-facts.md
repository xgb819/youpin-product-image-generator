# 商品事实与文案来源（项目工作规则）

本文件用于控制商品描述，不冒称官方版式条文，也不是法律合规自动裁定。字体/尺寸正确不能证明商品描述真实。

后台文字复用同一份事实记录，格式见 [listing-copy.md](listing-copy.md)。纯文字模式默认一次生成七字段，不逐字段重问；改单字段保留其余内容，审核按当前文字哈希复用。

## 记录什么

每个事实有稳定ID、原始值、单位、适用SKU、来源文件/对话定位、确认状态。来源类型区分厂家本款资料、实拍/用户确认、正式报告、近似款、竞品、AI图。保存原文和文件哈希以便对照，不能只留下AI摘要。

- 用户已确认的颜色、数量、同玩等事实可复用，不每改一张图都再问。
- 从图片识别的型号、尺寸、电池等先对照原文，明确测量对象；头部尺寸不能变为整条尺寸，包装尺寸不能变为机身尺寸。
- 近似款/竞品只提供风格和信息线索；需要本款证据才能迁移功能、材质、参数、赠品或年龄要求。
- 功能明确为无、或未知时，不能写为有。无灯光不能生成发光效果暗示该功能；音乐未知不能写“音乐互动”。
- “两台同玩”不扩成“任意多台/绝不串频”；“互动玩法”不扩成可验证的“提升专注力/开发智力”等效果承诺。
- 认证、检测、获奖、材质等级、适用年龄等核对对象、版本、报告/标识和适用范围；一句聊天确认不替代该类需要的正式证据。厂家原文也不自动等于已核准。

## 文案如何生成

先从已确认事实中选择信息，再压缩、组织语气。每条事实性文案绑定事实ID和它声称的值；创意性表达另标creative。未知项不出正式卖点，不为了固定六格、轮播张数或模板标题补功能。事实不足时可减少可选内容，或列出缺口，同时继续完成独立模块。

保留待审文案与已审文案状态。用户明确同意完整文案表或具体修改时记录原话/定位，再用于正式导出；只有“继续”且存在多个待确认项时不能替用户认定全部事实。不会因为AI做了一次自检就记成“用户确认”。现有会话中明确授权的常规措辞调整无需追加机械口令。

文案记录示意（在商品工作目录，不将真实客户资料入公共仓库）：

```json
{
  "facts": {
    "bean-count": {"value":7,"status":"confirmed","source":"本款配置表或用户确认定位","sku_ids":["green","beige"]}
  },
  "copy": {
    "kit": {"text":"每套7个数字豆","status":"draft","kind":"factual","assertions":[{"fact_id":"bean-count","equals":7}]}
  }
}
```

正式审核还需保留审核人/会话定位等可追溯记录。`assertions`只能检查绑定值是否一致，无法自动理解所有中文含义。例如把“绝不串频”错误绑定到“两台同玩”，结构可能有值却没有语义支持，必须人工排除。

脚本预览允许draft文案，但未知/矛盾事实仍拒绝；正式导出要求相关文案有approved状态与review记录、绑定事实已confirmed。此处approved不由渲染脚本自动填写，不意味着法律审核或实物验收已完成。其他未用于本张图的缺项不阻塞这一张的草稿。

## 修改后的追踪

事实值或SKU范围变化，查询所有引用该ID的图片并列出受影响清单。只改版式或等义措辞时按图ID重做；没有新增事实时沿用有效确认。图片中的数量、颜色、结构、按键、标识也在事实核对范围，AI图素不能作为这些事实的证据。
